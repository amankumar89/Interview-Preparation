## Fundamentals

### 1. What is Dependency Injection (DI)?

**Answer:** DI is a technique where an object receives the collaborators it needs from an external creator or container instead of constructing or locating them itself. It separates a class's behavior from the creation of its dependencies and makes the class easier to test with alternate implementations.

In Spring, the container performs this wiring from bean definitions and injection metadata.

### 2. What are the common types of dependency injection in Spring?

**Answer:** The commonly discussed forms are constructor, setter, and field injection. Constructor injection supplies required dependencies when an object is created. Setter injection supplies dependencies through mutators after construction and can be appropriate for optional or reconfigurable dependencies. Field injection writes directly into fields, commonly through reflection.

Spring supports all three, but constructor injection is generally preferred for required collaborators. It makes dependencies explicit, supports immutable fields, and lets the class be instantiated without reflection-based field mutation. Field injection also makes plain unit tests less convenient.

### 3. Why is constructor injection generally preferred for required dependencies?

**Answer:** A constructor makes the required dependencies part of the object's creation contract. The object cannot be constructed in an invalid partially wired state, and dependencies can be held in `final` fields. Tests can instantiate the class directly without starting Spring.

It also makes excessive coupling visible: a constructor with many dependencies is a useful signal to review the class's responsibilities. Constructor injection does not by itself solve poor design, but it makes that design pressure harder to hide.

### 4. How do you inject an optional dependency?

**Answer:** First decide whether the dependency is genuinely optional or whether the class has two distinct valid modes. For an optional collaborator, Spring provides options such as `Optional<T>`, `@Nullable`, or `@Autowired(required = false)` depending on the injection point and desired semantics. A setter can also express an optional dependency.

Prefer a clear absence value over silently constructing an incomplete object. If optional behavior creates complicated branches throughout the class, separate implementations or a no-op implementation may be clearer.

### 5. How does Spring handle multiple beans of the same type at an injection point?

**Answer:** A single-valued injection must resolve to one candidate. Spring can narrow candidates using `@Qualifier`, a matching bean name in supported resolution cases, or `@Primary`; otherwise, multiple eligible beans typically produce a `NoUniqueBeanDefinitionException`. `@Primary` selects a preferred candidate, while a qualifier states which semantic variant is required.

For a collection such as `List<PaymentProcessor>`, Spring can inject all matching beans. Use qualifiers to express intent rather than relying on incidental registration order.

### 6. What is circular dependency injection, and how should it be addressed?

**Answer:** A circular dependency occurs when creating one bean requires another bean that eventually requires the first. For example, constructor-injected `A` needs `B` while `B` needs `A`. Constructor cycles cannot be resolved by constructing either object first and normally cause context creation to fail.

Some setter or field cycles may be resolvable for singleton beans through early references, but that behavior is constrained and can interact badly with proxies and lifecycle callbacks. The durable fix is usually to remove the design cycle: extract shared behavior into a third collaborator, clarify ownership, or use an event or a narrower interface where appropriate. Lazy injection may defer a cycle, but should not be the default design fix.

### 7. How can a dependency with a shorter scope be used by a singleton?

**Answer:** If a prototype is injected directly into a singleton, the prototype is generally resolved when the singleton is created; it is not recreated on each method call. To obtain a fresh instance when needed, use a provider such as `ObjectProvider<T>` (or `Provider<T>`), or configure a scoped proxy where that scope is appropriate.

The singleton should depend on the provider abstraction and request the object at the point it needs it. This preserves the intended creation timing without manually managing the application context.

### 8. How would you unit-test a Spring service that uses constructor injection?

**Answer:** Instantiate it directly with a fake or mock dependency and test its behavior without loading an application context. This keeps a unit test fast and makes the service's dependencies explicit. Use a Spring context test only when the behavior under test includes container wiring, configuration, proxies, or other Spring infrastructure.
