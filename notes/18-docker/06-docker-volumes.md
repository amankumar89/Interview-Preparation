# Docker Volumes & Data Persistence

## Why Persistence Matters

Containers are meant to be **ephemeral** — their writable layer is deleted when the container is removed. Any data an application needs to survive container restarts, removal, or migration to another host must be stored **outside** the container's own filesystem layer, using volumes or bind mounts.

## Types of Data Storage in Docker

| Type | Managed By | Location | Use Case |
|---|---|---|---|
| **Volumes** | Docker | `/var/lib/docker/volumes/` (Docker-managed area) | Preferred for persistent app data |
| **Bind mounts** | User (you specify the path) | Any path on the host filesystem | Local development, sharing host config/code into a container |
| **tmpfs mounts** | Docker (memory only) | Host RAM | Sensitive, non-persistent, short-lived data (e.g., secrets in memory) |

## Volumes

Volumes are the **recommended** mechanism for persisting data generated by containers because Docker fully manages their lifecycle, they work identically across Linux/Windows/Mac, and they can be more easily backed up, migrated, or shared safely between containers.

```bash
docker volume create mydata
docker volume ls
docker volume inspect mydata
docker volume rm mydata
docker volume prune          # remove all unused (dangling) volumes

# using a volume
docker run -d -v mydata:/var/lib/mysql mysql
# equivalent, more explicit syntax:
docker run -d --mount source=mydata,target=/var/lib/mysql mysql
```

- If the named volume doesn't exist yet, Docker creates it automatically on first use.
- Volumes persist even after all containers using them are removed, until explicitly deleted (`docker volume rm` or `prune`).
- Multiple containers can mount and share the same volume simultaneously.

## Bind Mounts

Bind mounts map a specific host directory/file directly into the container.

```bash
docker run -d -v /home/user/app:/usr/src/app myapp
# or
docker run -d --mount type=bind,source=/home/user/app,target=/usr/src/app myapp
```

- Useful in local development for live-reloading source code into a running container.
- Tightly couples the container to the host's directory structure — less portable across machines.
- Host must already have the directory/file; permissions issues (UID/GID mismatches) between host and container are a common gotcha.

## `-v` vs `--mount`

Both achieve similar results, but `--mount` is more explicit and verbose, and is the **recommended** modern syntax, especially for complex configurations (like `tmpfs` options or read-only mounts).

```bash
-v mydata:/data:ro                                  # shorthand, read-only
--mount source=mydata,target=/data,readonly          # explicit form
```

Key differences:
- `--mount` fails explicitly with an error if the source doesn't exist (for bind mounts); `-v` silently creates a directory at that path.
- `--mount` syntax is more consistent and readable for volumes with many options.

## `tmpfs` Mounts

```bash
docker run -d --tmpfs /app/cache myapp
```

- Data is stored only in host memory (RAM), never written to disk.
- Automatically discarded when the container stops.
- Useful for temporary or sensitive data (e.g., avoiding writing credentials to disk).
- Only available on Linux hosts.

## Volume Drivers & Plugins

By default, volumes use the local driver (stored on the Docker host's disk), but Docker supports **volume plugins** for network/cloud storage — e.g., NFS, Amazon EBS, Azure File Storage, GlusterFS — enabling data to persist independent of any single host, which is important in clustered/orchestrated environments (Swarm, Kubernetes uses its own separate volume/PV system).

```bash
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.1,rw \
  --opt device=:/path/to/dir \
  nfsvolume
```

## Backup & Restore a Volume

A common pattern using a temporary helper container:

```bash
# Backup
docker run --rm -v mydata:/data -v $(pwd):/backup alpine \
  tar czf /backup/mydata-backup.tar.gz -C /data .

# Restore
docker run --rm -v mydata:/data -v $(pwd):/backup alpine \
  tar xzf /backup/mydata-backup.tar.gz -C /data
```

## Common Interview Questions

**Q: Why are volumes preferred over bind mounts in production?**
Volumes are fully managed by Docker (creation, permissions, backup tooling, drivers for remote/cloud storage), are portable across hosts and OSes, can be safely shared between multiple containers, and don't depend on a specific host directory structure existing. Bind mounts tightly couple the container to the host filesystem layout, which is fragile and less portable, though very convenient for local development.

**Q: What happens to a named volume if you remove the container that used it?**
Nothing — the volume persists independently of the container lifecycle unless you explicitly run `docker rm -v` (removes anonymous volumes associated with that container) or `docker volume rm`/`docker volume prune`.

**Q: How would you share data between two containers?**
Create a named volume and mount it into both containers (`-v shareddata:/path` on each `docker run`), or use a `volumes_from`-style pattern (legacy) or shared bind mount pointing to the same host path.

**Q: What's the risk of using bind mounts for sensitive host directories?**
A bind mount can expose sensitive host paths (e.g., `/etc`, `/var/run/docker.sock`) directly inside the container. Mounting the Docker socket, for instance, effectively gives the container root-equivalent control over the host's Docker daemon — a common privilege-escalation vector if misused.

**Q: Can you resize a running container's volume, and how do orchestration platforms handle persistent storage differently?**
Volume size is generally bound by the underlying storage driver/host disk (Docker's local volumes aren't inherently size-limited unless the driver enforces quotas). In orchestrated environments like Kubernetes, persistent storage is abstracted via **PersistentVolumes (PV)** and **PersistentVolumeClaims (PVC)**, decoupling storage provisioning from individual pods and supporting dynamic provisioning through StorageClasses — a more advanced and portable model than Docker's native volumes.
